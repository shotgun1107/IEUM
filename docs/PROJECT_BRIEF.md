# 이음 공식 프로젝트 기획 기준

기준일은 2026년 10월 2일이며, 현재까지의 대화와 공식 인계를 정리한 문서입니다. 이 문서의 목적은 다른 환경에서도 같은 출발점에서 기획을 이어가는 것입니다. 승인된 최종 제품 명세는 아닙니다.

## 확정된 프로젝트 지위

사용자는 이음을 공식 프로젝트로 승격하고 이 프로젝트의 메인 AI를 공식 총괄로 지정했습니다. 이전 아이디어 정리 작업은 여러 아이디어의 초기 정리를 돕는 역할로 남습니다. 인수한 것은 이음의 아이디어와 자료·논의입니다.

현재 명칭은 **이음 — AI 중심 프로젝트 지식 관리**이고, 공개 GitHub 저장소 이름은 **IEUM**입니다. 사용자 요청 없이 이름 재선정을 시작하지 않습니다. 이전 후보 이음·IEUM, 정합·JEONGHAP, 문맥·MUNMAEK, Concord, Weave 중 이전 AI가 이음을 추천한 이력은 있으나, 상표와 도메인 사용 가능성은 미확인입니다.

## 사용자가 해결하려는 문제

AI가 문서를 기준으로 개발하려면 기획과 요구사항의 기반이 충분히 명확해야 합니다. 규모가 커질수록 같은 사실이나 전제가 여러 문서에 흩어지고, 한 문서의 변경이 다른 문서에 반영되지 않아 불일치가 생깁니다. 문서 작성·수정·탐색과 AI가 읽고 이해해 작업하는 시간·비용도 커집니다.

사용자는 발전된 LLM 위키, AI를 위한 문서 체계, 연결된 지식 구조를 출발점으로 제시했습니다. 목표는 지식을 만들어 두는 데 그치지 않고, 변경 이후에도 AI가 필요한 기준과 맥락을 정확하게 사용할 수 있도록 하는 것입니다.

## 적용 범위

우선 한 프로젝트에서 아이디어 확정 이후의 기획·요구사항·명세·문서 작성부터 AI의 개발 및 변경 관리까지 이어지는 지식 기반을 다룹니다. 첫 대상 사용자, 프로젝트 규모, 문서 종류와 변경 빈도는 미정입니다.

사용자가 별도로 진행 중인 장기 프로젝트는 AI 개발의 성공·실패·판단 근거를 축적해 다른 AI와 다른 프로젝트가 이어받는 중앙 지식 시스템입니다. 이번 기획을 그 범프로젝트 시스템으로 확장하기로 한 결정은 없습니다.

## 사용자의 중심 구조

| 단계 | 책임과 동작 |
|---|---|
| 지식 구성 | 문서 또는 지식 단위가 다른 단위의 기준·전제가 되며 서로 의존합니다. |
| 모듈 구성 | 관련 문서를 묶고 모듈에 담당 AI의 책임 범위를 둡니다. |
| 영향 추적 | 변경이 발생하면 코드·자동화가 의존 관계를 따라 영향받는 문서와 모듈을 찾습니다. |
| 의미 판단 | 해당 단위의 Jev가 변경 때문에 기존 문서에 모순·불일치가 생겼는지 판단합니다. |
| 수정 | 필요한 경우 해당 모듈의 Luna가 문서를 수정합니다. |
| 후속 전파 | 수정이 다른 문서에 영향을 주면 의존 관계를 따라 다시 검토합니다. |

영향 대상을 찾는 자동화와 의미적 불일치를 판단하는 Jev는 역할이 다릅니다. 처음부터 모든 문서의 변경 영향을 Jev 혼자 찾는 구조로 바꾸지 않습니다.

빠르고 저렴한 판단·수정은 기대 효과이며 이 프로젝트에서 검증되지 않았습니다. Jev·Luna 조합은 중심 검증 가설입니다. 구체적인 모델 ID, 버전, API, 요금과 호출 기준은 정하지 않았습니다.

모든 문서마다 상시 실행 AI를 하나 두는 것은 확정 사항이 아닙니다. 모듈별 책임과 필요시 호출은 이전 AI가 제안한 운용 형태입니다. DFS는 탐색 방식의 예로 언급됐으며 필수 알고리즘은 아닙니다.

## 표현과 구조에서 아직 열려 있는 선택

사용자가 지식 단위를 변수, 문서 묶음을 class·def로 설명한 취지는 참조 가능한 지식 단위, 기능·업무별 모듈, 명시적 의존 관계, 변경 영향 분석과 전파로 정리할 수 있습니다. 실제 프로그래밍 언어를 만들기로 확정한 것은 아닙니다.

옵시디언의 연결 구조와 뇌처럼 필요한 부분을 선택적으로 활성화하는 구조는 발상에 영향을 준 직관입니다. 뇌 모방의 우월성이 검증됐거나 생물학적 구현이 요구된 것은 아닙니다.

“AI 전용은 사람이 못 읽는 언어를 뜻할 필요가 없고 AI 정확성과 전체 비용을 우선한다”는 해석은 이전 AI의 제안입니다. 사용자가 독자 표현 체계를 포기했다고 단정하지 않습니다. 자연어, 구조화 필드, 별도 문법의 조합은 미정입니다.

## 이전 AI가 제안한 설계 후보

아래 내용은 기존 논의의 연속성을 위한 제안 목록입니다. 모든 항목이 사용자에게 최종 승인된 것은 아닙니다.

- 지식 단위에 ID, 제목, 내용·범위·예외, 상태·버전, 출처·권한, 의존 관계와 검증 기준을 필요한 수준으로 둡니다.
- 포함 관계, 관련 링크와 의존 관계를 구분합니다. 반복 사실은 참조하고, 다른 사실에서 도출한 판단은 의미 검토 대상으로 둡니다.
- 변경 → 영향 분석 → Jev 판단 → Luna 임시 수정안 → 검증 → 반영의 흐름을 둡니다. 여러 문서의 변경을 하나의 논리적 변경 집합으로 다룹니다.
- 반복·순환·버전·중복 처리와 종료 조건을 통제합니다. 구체적인 트랜잭션·롤백 방식은 미정입니다.
- 당장 개발할 기능에 필요한 충분한 기준을 먼저 갖추고, 검색 결과에 필요한 전제와 예외를 조립해 제공합니다.
- 실제 사용 실패를 기록하되 AI 관찰을 즉시 확정 지식으로 승격하지 않습니다.

문서 유지보수와 운영 방식 개선은 별도 과정으로 제안됐습니다. 전자는 승인된 요구사항에 문서를 맞추는 작업입니다. 후자는 검사 질문, 표현 구조, 검색, 맥락과 호출 정책을 비교·개선하는 작업입니다. RRSI는 후자의 참고 후보이며 MVP 포함 여부는 미정입니다. 운영 최적화가 요구사항이나 채택 기준을 임의로 완화하도록 허용한 적은 없습니다.

## 검토 자료가 제시한 주요 판단

[통합 검토 보고서](research/integrated-review.original.txt)의 주장을 이 프로젝트에서 이미 확인한 성능과 구분합니다. 세부 출처와 확인 한계는 [자료 안내](research/README.md)에 정리했습니다.

- 구성 요소가 특정 환경에서 효과를 보였다는 사실만으로 통합 시스템이 더 단순한 대안보다 우월하다고 결론 내릴 수 없습니다.
- 원천부터 구조화하는 방식과 기존 원문 위에 검색·관계 계층을 만드는 방식을 비교할 수 있습니다. 두 방식 모두 최신성 유지 부담이 있습니다.
- 자기완결성은 모든 전제를 복사하는 것으로 한정하지 않습니다. 대상·범위·필요 전제를 식별하고 제공 시 조합하는 방안이 제안됐습니다.
- 의존성 그래프도 누락과 오류가 있는 관리 대상입니다. 등록된 관계 밖의 영향을 발견하는 방법이 필요할 수 있습니다.
- 관련성, 정보 충분성, 정합성, 현행성·권한, 정확성·요구사항 충족을 구분해야 합니다.
- 재검토 결과 본문이 여전히 유효하면 불필요하게 수정하지 않고 검증 이력만 갱신할 수 있어야 한다는 제안이 있습니다. 문서 버전과 현재 유효성은 다릅니다.
- 구현과 문서의 충돌은 오래된 설명, 구현의 요구사항 위반, 아직 결정되지 않은 요구사항 중 무엇인지 확인해야 합니다.
- 역할을 나누어 오류를 평가하는 것과 별도 Jev·Luna 호출의 경제성은 다른 가설입니다. RRSI의 실행 토큰 비용도 전체 도입·승인·관계 유지·평가·복구 비용과 다릅니다.
- AI의 초안·관계 후보 생성이 작성자의 부담을 검토자에게 옮기는지 측정해야 합니다.

“전체 비용을 평가해야 한다”, “통합 체계는 아직 검증 가설이다”는 이전부터 알려진 사항입니다. 후속 조사의 새 발견으로 중복 계산하지 않습니다. 기존 구성 요소에 선례가 있으므로 통합만으로 학술적 신규성이나 유일성을 주장하지 않습니다.

## 검증 방향 후보

사용자 확정 평가 계획은 아직 없습니다. 이전 검토에서는 기존 문서와 기본 검색·검토를 기준으로 의존성 관리, AI 판단·수정, 운영 개선을 추가했을 때의 효과를 구분하는 비교를 제안했습니다.

검증 지표 후보는 변경 누락, 불필요한 수정, 근거 검색 성공, 요구사항·조건·예외 보존, 개발 결과의 정확성입니다. 비용에는 도입, 내용과 관계의 유지, 검색·색인·캐시, AI 호출, 검토·승인, 복구·재작업, 운영 개선 실험을 포함합니다. 사람의 시간, 연산과 지연을 먼저 구분하고 비용 환산 기준은 별도로 정해야 합니다.

오류는 영향 대상 탐색 누락, Jev 오판, Luna의 예외 삭제, 검증의 잘못된 통과, 개발 AI에 대한 맥락 제공 실패로 나누어 볼 수 있습니다. 단순 값 변경 외에도 적용 범위 변경, 예외 추가, 요구사항 철회, 상위 기준 충돌, 정보 부족 사례가 필요하다는 제안이 있습니다.

비용 절감만이 채택 기준은 아닙니다. 필수 품질을 지키면서 중요한 오류 감소가 추가 비용을 정당화하는지도 검토할 수 있습니다. 성공 기준과 중단 기준은 미정입니다.

## 아직 결정해야 할 사항

| 결정 영역 | 남아 있는 질문 |
|---|---|
| 첫 적용 범위 | 대상 사용자, 프로젝트 규모, 문서 종류와 변경 빈도 |
| MVP와 평가 | 첫 대표 작업, 비교 대상, 성공·중단 기준 |
| 정보 표현 | 원천 구조화 또는 파생 계층, 문법·스키마, 지식 단위 크기 |
| 모듈과 관계 | 모듈 경계, 의존 관계 생성·검증·유지·삭제와 누락 탐지 책임 |
| 모델 운용 | Jev·Luna 버전·API, 판단 질문·임계값·보정, 맥락·권한, 인간 검토 범위 |
| 변경 관리 | 변경 집합, 원자적 반영, 순환·중복·종료, 버전·롤백 |
| 지식 제공 | 검색, 전제·예외 조립, 색인 갱신과 캐시 일관성 |
| 품질과 권한 | 수정 검증, 요구사항 우선순위, 평가 기준 변경 권한 |
| 운영 개선 | RRSI를 MVP에 포함할지, 후속으로 분리할지 |

현재 메인 AI의 다음 단계 제안은 **한 프로젝트에서 요구사항 하나가 바뀌었을 때 관련 명세·설계·테스트 문서를 찾아 일관되게 갱신하는 과정**을 첫 검증 대상으로 검토하는 것입니다. RRSI의 추가 효과를 별도로 평가하는 순서도 제안했습니다. 이 제안은 아직 사용자가 확정한 MVP가 아닙니다.

## 예시와 실제 정책의 구분

기존 논의의 탈퇴 정책 “즉시 삭제 → 7일 철회 가능”은 영향 전파를 설명하는 예시였습니다. 탈퇴 절차·화면 안내·데이터 삭제·테스트의 연계와 Jev 판단, Luna 수정, 변경 집합 검증을 보여주기 위한 것입니다. 7일이라는 값과 해당 서비스 정책을 이음의 실제 요구사항에 넣지 않습니다.

이 예시에서 철회 기간 로그인 가능 여부나 실제 개인정보 삭제 시점은 주어진 조건에 없으므로 미해결 요구사항으로 남습니다. 누락된 삭제 문서를 발견했을 때 관계 등록·검색 개선 후보를 만들고 다른 사례로 평가한다는 설명도 설계 예시입니다.

## 실제 수행 상태

현재까지 이음에서는 문헌·기획 논의와 인계 자료 검토만 수행했습니다. Jev·Luna 호출, RRSI 실행·벤치마크 재현, 의존성·검색·검증 엔진 구현, 비용 측정은 하지 않았습니다.

이전 아이디어 정리 프로젝트의 AGENTS.md, README.md, 수동 판단 사례 11개와 빈 아이디어 폴더 표시는 그 프로젝트의 운영 자료였습니다. 이음 시스템이나 자동 평가 엔진의 구현으로 계산하지 않으며 이 저장소에 복사하지 않습니다. 이전 통합 발표문은 대화로 작성됐다고 인계됐고, 별도 공식 명세 파일이 확보된 것은 아닙니다.
